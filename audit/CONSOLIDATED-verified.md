## [HIGH] Moved-data pointer scheme can resolve to the wrong directory or strand the vault entirely
- **where:** identilock/config.py:96  (durability-and-correctness)
- **scenario:** (1) Stranding: after 'move my data' the success message says 'The old copy stays at <old dir> — delete it yourself'. A user who deletes that folder also deletes prefs.json — the only pointer to the new location. Next launch, default_data_dir() has no pointer and no database, so is_initialized is false and the app shows the first-run setup screen; a non-technical coworker concludes their SSNs/PINs are gone, or runs setup and creates a fresh empty vault shadowing the real one. (2) Wrong resolution: move A->B, later delete only B's... rather A's identilock.db (as the 'move that file out of the way' error instructs) and move B->A. write_prefs merges, so A's prefs retain the stale data_dir=B alongside the fresh copy; load_settings follows A->B, then B's data_dir=A hits the `candidate in seen` break, and the app silently keeps running from B — the copy the user was just told is old and deletable. (3) write_prefs is a non-atomic truncate-and-write; a crash mid-write corrupts the pointer with the same stranding effect.
- **verified:** Verified by tracing the code. write_prefs (config.py:36-45) reads existing prefs and prefs.update(updates) — it never removes keys unless explicitly set to None, and move_data_dir (settings_routes.py:141-142) writes only lock_minutes to the target, so a stale data_dir at the destination survives. The round-trip is reachable: move_data_dir refuses a target containing identilock.db and tells the user to 'move that file out of the way first', which removes the db but not prefs.json. load_settings' loop (config.py:97-105) with seen={A}: A->B (B added to seen), B's prefs say A, A in seen -> break, resolved_dir=B. The deletion scenario follows the app's own instruction verbatim ('The old copy stays at {data_dir} — delete it yourself'), and after deletion resolution lands on an empty default dir -> setup screen. write_prefs uses Path.write_text directly, non-atomic. No data is cryptographically destroyed — the vault file survives intact at the other location — but for the stated audience (non-technical coworkers) the practical outcome is a believed-lost vault or a shadow vault splitting new data, which is a durability failure the app itself induces. High is appropriate.
- **fix:** In move_data_dir, clear any stale pointer at the destination: write_prefs(target, lock_minutes=..., data_dir=None) (write_prefs already drops None values). At startup, when the resolved directory contains identilock.db, self-heal by rewriting its prefs without a data_dir key. Make write_prefs atomic (write to a temp file, then os.replace). Reword the success message to name the exact file to delete (identilock.db) and warn against deleting the folder; optionally have load_settings fall back to any pointer-chain hop that still contains identilock.db before declaring the vault uninitialized.

## [HIGH] User-entered reminder title and detail are stored in cleartext
- **where:** identilock/db.py:135  (data-at-rest-confidentiality)
- **scenario:** A user creates a custom reminder such as 'Thaw Experian for Sarah before closing — PIN 4821'. The laptop or a synced copy of identilock.db is stolen; `strings identilock.db` prints the name and PIN in the clear, despite the backup UI (identilock/routes/settings_routes.py:279-281) promising the file is 'useless without' the passphrase.
- **verified:** Verified in code: reminders.title and reminders.detail are plain TEXT (db.py:135-136); repo.create_reminder (identilock/repo.py:572-576) inserts user-typed free text unencrypted; ENCRYPTED_FIELDS['reminders'] lists only notes_enc, which no form or route ever populates. The db.py docstring (line 6) claims 'free-text notes' are encrypted, and the app itself concedes reminder titles 'include family members' names' (identilock/templates/reminders.html:48) — for the calendar export it warns, but for at-rest storage it does not. The reminders form ('What'/'Detail' inputs, reminders.html:69-96) gives no cleartext warning. This is a direct priority-1 confidentiality leak under the stated theft-of-file threat model, so high severity is correct.
- **fix:** Add title_enc/detail_enc BLOB columns via _ensure_column, register them in ENCRYPTED_FIELDS, seal in create_reminder/seed_reminders_for and open in list_reminders (the only SQL ordering used is due_date, which stays cleartext), and migrate existing plaintext rows on first unlock. Until then, the reminders form should state these fields are stored unencrypted.

## [HIGH] User-typed reminder text and report filenames are stored in plaintext, contradicting the 'everything is scrambled' claims
- **where:** identilock/db.py:135  (honesty-of-claims)
- **verified:** Reproduced in code: db.py declares reminders.title/detail as plain TEXT (lines 135-136) and ENCRYPTED_FIELDS lists only notes_enc for reminders (line 50); repo.create_reminder inserts the user's title/detail directly into those columns with no vault involvement, and routes/reminders.py reminder_create passes free-text form input straight through. reports.source_name (db.py:150) likewise stores the uploaded filename in the clear via save_report (repo.py:635-641, routes/reports.py:99). The contradicted absolute claims are verbatim in help.html:16 ('Everything you type is saved into one scrambled (encrypted) file'), help.html:78 (lost USB is 'gibberish'), settings.html:15-17 ('unreadable without your passphrase'), and the move-kit success message (settings_routes.py:251-256, 'useless without the passphrase'). db.py's own 'Left in the clear' docstring (lines 9-14) omits these fields and claims a thief 'learns no identities' — false once a reminder names a family member or a report filename contains one. This is both a priority-1 confidentiality defect (names/context readable in the stolen file, the exact threat the app defends against) and a priority-3 honesty defect, so high severity holds.
- **fix:** Encrypt user-entered reminder text (add title_enc/detail_enc BLOBs following the existing notes_enc pattern, migrate existing rows via _ensure_column plus a backfill under the vault key, and add them to ENCRYPTED_FIELDS so passphrase changes re-wrap them) and encrypt or stop storing reports.source_name. Correct the db.py 'Left in the clear' docstring; until the schema fix ships, soften the absolute claims in help.html, settings.html, and the move-kit message.

## [HIGH] Auto-backup catches only OSError; sqlite3 errors block unlock, and failed backups poison the backup set
- **where:** identilock/routes/auth.py:48  (durability-and-correctness)
- **scenario:** Disk fills. On unlock, db.backup_to raises sqlite3.OperationalError, which escapes the `except OSError` at auth.py:48 and turns unlock_submit into a 500 — the exact failure the docstring promises to swallow. sqlite3.connect creates the destination file before the copy, so a partial identilock-auto-*.db is left behind; its fresh mtime matches the identilock-*.db glob and suppresses further auto-backups for 7 days (this also means the second unlock attempt usually succeeds — the blocking is typically one attempt, not indefinite — but the corrupt file persists). Name-sorted pruning (automatic[:-10]) then discards older good backups while retaining the corrupt newest ones, so when a backup is actually needed the newest copies are unreadable. The manual /settings/backup route (settings_routes.py:273) has no exception handling at all, and move_data_dir/make_move_kit catch only OSError around backup_to.
- **verified:** Every element checks out in code. sqlite3.OperationalError inherits sqlite3.Error -> Exception, not OSError, so the except clause at auth.py:48 does not cover it. db.backup_to (db.py:387-396) opens sqlite3.connect(destination) directly at the final name with no temp-file/os.replace step, so the file exists before the copy completes. The glob at auth.py:38 is 'identilock-*.db', matching both manual and auto backups including a truncated one, and the pruning at auth.py:45-46 sorts by name (timestamp-embedded, so chronological) keeping the newest 10 regardless of validity. settings_routes.py:273 calls db.backup_to bare. The only overstatement in the claim is 'cannot be opened at all until space is freed' — in the common sub-case the partial file's mtime makes the retry skip the backup and unlock succeeds; only if file creation itself fails does every unlock 500. The backup-set poisoning is the durable harm and squarely hits audit priority 2 (durability), justifying high.
- **fix:** In _maybe_auto_backup catch (OSError, sqlite3.Error) as the docstring intends. In db.backup_to, back up to destination.with_suffix('.tmp') and os.replace() onto the final name only after conn.backup completes, unlinking the temp on failure (optionally run PRAGMA integrity_check on the copy first). Wrap /settings/backup in try/except (OSError, sqlite3.Error) rendering an error message, and widen the excepts around backup_to in move_data_dir and make_move_kit the same way.

## [HIGH] Uploaded credit reports are written to an unencrypted OS temp file, contradicting the in-app claim
- **where:** identilock/routes/reports.py:70  (web-attack-surface)
- **verified:** Every technical claim checks out against the installed Starlette. formparsers.py:147 sets MultiPartParser.spool_max_size = 1024*1024 and line 230 backs each file part with SpooledTemporaryFile(max_size=self.spool_max_size), so any upload past 1 MB rolls over to a real tempfile.TemporaryFile in the OS temp directory. formparsers.py:184 applies max_part_size only when _current_part.file is None, so file parts are indeed unbounded. reports.py:70 does 'data = await upload.read()' and the MAX_UPLOAD_BYTES check is at line 73 — after parsing, so it cannot prevent the spill. Meanwhile reports.py:90-91 states 'The uploaded file itself is never written to disk' and templates/reports.html tells the user Identilock 'keeps only the words from the file, scrambled (encrypted) into its database on this computer'. Both are false for the common case of a multi-MB bureau PDF containing the full SSN. This lands squarely on audit priority 1, which names temp files explicitly, and on priority 3 (honesty). Platform nuance worth noting but not disqualifying: on Linux tempfile.TemporaryFile uses O_TMPFILE so no other process can open it by path; on Windows — the stated coworker platform — it is a named %TEMP% file, and on all platforms the plaintext blocks remain unwiped after close on a machine without full-disk encryption. Keeping the reviewer's 'high': plaintext SSN-bearing data reaches the disk in the clear and the app states the opposite.
- **fix:** Reject POST /reports before parsing when Content-Length exceeds MAX_UPLOAD_BYTES (middleware or dependency), then raise starlette.formparsers.MultiPartParser.spool_max_size above that cap at startup so the body never rolls to disk. Fix the comment at reports.py:90-91 and the hint in templates/reports.html to match whatever the code actually does.

## [HIGH] Uploaded credit reports over 1MB are spooled to a plaintext temp file on disk despite the 'never written to disk' claim
- **where:** identilock/routes/reports.py:90  (honesty-of-claims)
- **verified:** Reproduced against the installed Starlette in .venv: MultiPartParser creates SpooledTemporaryFile(max_size=spool_max_size) with spool_max_size = 1MB for every file part (formparsers.py:147, 230), and the max_part_size guard in on_part_data applies only to non-file parts (the file branch appends to _file_parts_to_write with no size check), so file parts larger than 1MB roll over to a real temp file in the OS temp directory. This happens during form parsing, before the handler's upload.read() and before the MAX_UPLOAD_BYTES (25MB) check in reports.py:73 can reject anything. Bureau PDFs routinely exceed 1MB, so the full plaintext report — SSN, accounts, addresses — is written unencrypted to disk on upload; the unlinked file's blocks persist and are forensically recoverable. crypto.py's threat model explicitly includes 'stolen laptop', so this is in scope, and audit priority 1 names 'temp files' as the exact confidentiality question — which is why I raised this from medium to high: the leaked content is the most sensitive data the app handles, the code comment at reports.py:90 and the reports.html:61 hint both assert the opposite, and the leak requires no user mistake. The /setup/import path uses the same mechanism but spools an already-encrypted vault, so it is not a disclosure.
- **fix:** Bypass the spooled parser for this route: stream request.body()/request.stream() into an in-memory buffer with an incremental MAX_UPLOAD_BYTES cap and parse the multipart body in memory, or configure the parse with a spool threshold above MAX_UPLOAD_BYTES so the part never leaves RAM (e.g. call request.form() with a raised spool size where the installed Starlette allows, or subclass the parser). At minimum, correct the reports.py comment and the reports.html claim so they match actual behavior, and note the temp-file exposure.

## [MEDIUM] Corrupted ciphertext decrypts to None, indistinguishable from empty, and is destroyed on next save
- **where:** identilock/crypto.py:150  (crypto-key-management)
- **verified:** Verified in code: Vault.decrypt (crypto.py:145-150) maps InvalidTag/ValueError to None, the same value as a NULL blob. The person edit form prefills from decrypted values, so an unreadable field renders blank, and update_person (repo.py:144-171) unconditionally re-encrypts every column from form values, writing NULL over the original ciphertext on any save of that person. The one safeguard that exists — the SSN 'blank means keep' logic at routes/people.py:266-271 — preserves existing.ssn, the DECRYPTED value, which is None for an unreadable blob (and has_full_ssn is False so the store_full_ssn checkbox renders unchecked), so even that field is destroyed. This is a durability defect (audit priority 2) in-scope for the theft/restore threat model: crypto.py:148-149 itself anticipates the partial-restore-under-another-passphrase state, and the docstring's 'integrity nuisance rather than a disclosure' claim is contradicted by silent, permanent loss (priority 3 honesty). Medium, not high: it requires a corrupt or key-mismatched blob to exist first, and destruction needs a subsequent edit of that record.
- **fix:** Make decryption failure a distinct state (raise or return a sentinel such as Undecryptable instead of None in Vault.decrypt), render such fields as 'unreadable — wrong passphrase or corrupted data' in templates, and in update paths carry the stored blob through unchanged when the corresponding field is unreadable rather than overwriting it with NULL.

## [MEDIUM] Decrypt failure returns None, indistinguishable from empty; a subsequent save silently overwrites the ciphertext with NULL
- **where:** identilock/crypto.py:150  (durability-and-correctness)
- **scenario:** A cloud-sync tool half-restores an old identilock.db or a disk error corrupts pages: several blobs fail AES-GCM authentication. Vault.decrypt returns None for each — identical to a legitimately blank field — so the person renders with empty SSN/notes/DOB, has_full_ssn False, and display_name as the literal '(unreadable)' (repo.py:79), with no warning anywhere. The user fixes an unrelated typo and saves: update_person (repo.py:139-171) re-encrypts every field from the round-tripped form, writing NULL over the surviving ciphertexts and '(unreadable)' as the person's real name. letters._mark_mailed (letters.py:82) does the same to pin_enc/confirmation_enc with no user form involved. The diagnostic ciphertext is destroyed, and the window to restore from a good backup passes with the user never told anything was wrong.
- **verified:** Confirmed at every step. crypto.py:142-150: InvalidTag/ValueError -> None, conflated with the None returned for an absent blob. repo.py:71-81 builds the Person from those Nones and substitutes '(unreadable)' for the name — a string the edit form then submits as data. update_person unconditionally re-encrypts all eight fields from form values, and Vault.encrypt maps None/'' to NULL, so a save after a decrypt failure replaces still-present ciphertext with NULL. _mark_mailed passes existing.pin/confirmation/notes back through update_freeze_record, so even a click on 'mark mailed' with no form nulls a failed-to-decrypt PIN. ## [MEDIUM] One undecryptable blob makes passphrase change — and therefore recovery — fail entirely
- **where:** identilock/db.py:310  (crypto-key-management)
- **verified:** Verified in code: change_passphrase (db.py:296-327) calls open_sealed on every non-NULL blob across all ENCRYPTED_FIELDS with no per-field error handling; the blanket except rolls back and re-raises. Neither caller catches it — settings_routes.py:207 and auth.py:223 — and the app's only exception handler is for HTTPException (web.py:120), so both routes return an unhandled 500. In /recover this occurs AFTER recover_data_key has already verified the code against the verifier (db.py:382), so a cryptographically correct recovery credential cannot open the vault through the UI if even one blob (e.g. a freeze_records notes_enc) is corrupt. ## [MEDIUM] Recovery re-wrap is committed separately from passphrase change, leaving a window where the recovery credential is silently destroyed
- **where:** identilock/db.py:324  (crypto-key-management)
- **verified:** Verified in code: change_passphrase commits at db.py:324; set_recovery commits independently at db.py:355; all three call sites sequence them as separate transactions (settings_routes.py:207-209, auth.py:223-225, setup at auth.py:89-93). Between the commits the database holds data and verifier under the new key while recovery_wrap still wraps the old key under the old code — recover_data_key would unwrap the old key, fail the verifier check (db.py:382), and report it as a wrong code. The window is wider than a pure crash race: set_recovery performs a full Argon2id derivation (64 MiB, time_cost 3) between the two commits, roughly a second on the old laptops this app targets, and any set_recovery failure (disk full) 500s the route so the new code is never displayed. Mitigations keep this at medium rather than high: passphrase changes are rare events, and at the moment of failure the user still knows the new passphrase, so loss only materializes if it is later forgotten — but that is exactly the case recovery exists for, the disarming is silent, and the printed Identilock-Recovery-Code.txt explicitly tells the user the code is replaced on passphrase change, so they believe they are covered (priority 3 honesty). The setup-path window (auth.py:89-93) is the mildest case since a crash there just leaves has_recovery false, which /recover reports honestly.
- **fix:** Fold the recovery re-wrap into change_passphrase's single transaction: generate the new code and write recovery_salt/recovery_*/recovery_wrap (sealed under the new key) before the single commit at db.py:324, returning (new_vault, code) for the caller to display. Apply the same single-transaction pattern to initial setup.

## [MEDIUM] Recovery wrap is not updated inside the change_passphrase transaction; a crash leaves has_recovery=True with a dead wrap
- **where:** identilock/db.py:283  (durability-and-correctness)
- **scenario:** User changes their passphrase; the laptop dies right after change_passphrase's transaction commits but before the separate set_recovery commit — a window widened to seconds by set_recovery's Argon2 derivation (KdfParams.generate + derive_key at db.py:348-349). The stored recovery_wrap still wraps the retired data key while has_recovery() reports True. ## [MEDIUM] /setup and /setup/import accept cross-origin POSTs, letting a web page set the vault passphrase on a fresh install
- **where:** identilock/routes/auth.py:231  (web-attack-surface)
- **verified:** Verified in code. POST /setup (auth.py:68), POST /setup/import (auth.py:231) and POST /recover (auth.py:185) take no csrf_token parameter and never call verify_csrf; the corresponding templates (setup.html, recover.html, unlock.html) contain no csrf field at all (grep for 'csrf' in them returns nothing). A repo-wide grep for Origin/Referer/Sec-Fetch/TrustedHost in identilock/ returns nothing, and web.py:101-118 installs only a response-header middleware, so no request-side origin check exists. Both endpoints are reachable with no cookie (no get_session/require_session dependency), so SameSite=strict is irrelevant to reaching them, and the app's own CSP form-action 'self' constrains the app's pages, not the attacker's. A cross-origin auto-submitting form therefore does call db.initialize_vault(conn, passphrase) with an attacker-chosen passphrase, or replaces the fresh DB via /setup/import. Two corrections that lower the severity from the reviewer's 'high': (a) both endpoints are hard-gated by 'if db.is_initialized(conn): return redirect(...)', so the entire window is the minutes between install and first passphrase — after that the gap is unexploitable, and /recover additionally needs a valid recovery code, so it is not attackable at all; (b) the 'victim finds it already unlocked' step needs the Set-Cookie to actually stick, which only holds for a top-level form navigation (visible to the user, and useless if they run the default pywebview window, which has its own cookie jar) — in a hidden iframe modern third-party-cookie blocking drops it, leaving only lockout/DoS on an empty vault. The defect is real and the fix is cheap, but the reachable worst case is narrower than described.
- **fix:** Issue a random pre-session cookie plus a matching hidden token on GET /setup and GET /recover and verify it on the matching POSTs, and/or add one middleware in create_app that rejects any non-GET/HEAD request whose Origin is present and not the app's own origin, or whose Sec-Fetch-Site is neither same-origin nor none. The middleware closes this class for every current and future endpoint at once.

## [MEDIUM] Move file and recovery code are both dropped on ~/Desktop with default permissions — the app violates its own warning

## [LOW] No Host-header validation, so a remote site can reach the loopback app via DNS rebinding
